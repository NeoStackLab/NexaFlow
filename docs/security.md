# Security model

## Authentication

- Passwords are hashed with bcrypt cost 12 and are never returned by the API.
- Access tokens are HS256 JWTs with issuer, subject, token ID, issue time,
  expiration, roles, and permission claims. The default lifetime is 15 minutes.
- Refresh tokens are 256-bit opaque random values. Only their SHA-256 hashes are
  stored in PostgreSQL.
- A successful refresh revokes the previous session and inserts its replacement
  in one row-locked transaction, preventing concurrent token reuse.
- Logout revokes the supplied refresh session. Users may list and revoke their
  own active sessions by ID.
- Production refuses to start with the development JWT signing secret.

The web application stores the token pair in `sessionStorage`, not persistent
local storage. This preserves a session across same-tab navigation but clears it
when the browsing session ends. Two concurrent protected requests share one
refresh operation so single-use rotation is not raced by the client.

## RBAC

Four roles are installed by default:

| Role | Default capability |
| --- | --- |
| `super_admin` | Every seeded permission; permission set is immutable. |
| `admin` | Dashboard, users, user creation, and order viewing. |
| `employee` | Dashboard and order viewing. |
| `guest` | Dashboard viewing only. |

Public registration always assigns `employee`; callers cannot select a role.
RBAC mutations require `role.manage`, user listing requires `user.view`, and
middleware validates access-token permissions before the handler runs. Role
permission replacement and user role replacement are transactional.

Dynamic navigation is generated by the backend from current effective
permissions. The UI is not an authorization boundary; protected APIs enforce the
same permission independently.

## Tenant isolation

- Access JWTs contain a mandatory active `tenant_id`; tenant-less legacy tokens
  are rejected.
- Refresh sessions are bound to a tenant. Refresh preserves that tenant.
- Tenant switching verifies active membership and atomically rotates the refresh
  session into the target tenant before issuing a new access JWT.
- Protected middleware revalidates membership on every request. `X-Tenant-ID`
  may assert the token tenant but can never override it.
- Verified authentication is promoted into a `TenantContext` containing tenant,
  user, primary role, roles and permissions. The same Go context reaches the
  service and repository layers.
- Business repository calls fail before querying when tenant context is absent.
  Login, installation and cross-tenant workers must opt into a distinct trusted
  system context; there is no implicit bypass.
- Every repository call uses a database transaction with transaction-local
  tenant/user settings. Forced PostgreSQL row-level-security policies apply the
  tenant predicate to reads and writes, including raw SQL, and prevent pooled
  connections from retaining tenant state.
- The application database role must be `NOSUPERUSER NOBYPASSRLS`; startup
  migration refuses an unsafe role. Compose creates a separate bootstrap admin
  and non-privileged application owner because PostgreSQL superusers always
  bypass RLS, even when table owners are forced through policies.
- Role assignments, role grants, user lists, session lists, and session
  revocation all require tenant scope at the Go repository interface.
- Query caches are invalidated after browser tenant switching so menus and RBAC
  data from the prior tenant are never reused.

Tenant suspend, archive and soft-delete operations revoke all active refresh
sessions. The designated primary tenant is protected from lifecycle changes;
an operator must first move primary-tenant responsibilities through a future
administrative recovery workflow. Soft deletion is not a regulatory purge;
export, retention and delayed physical deletion remain roadmap work.
